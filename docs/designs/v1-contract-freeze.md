# Design: Lean Oracle v1 contract freeze

Generated by /office-hours on 2026-09-26
Branch: main
Repo: calledAdo/lean-oracle-v2
Status: APPROVED
Mode: Startup (ecosystem, open-source infrastructure)

## Problem Statement
Lean Oracle v2 works on testnet, but its on-chain contracts are immutable (no upgrade key), and the
current versions freeze in choices that would hurt integrators. Lean Oracle is an open-source,
community price oracle: anyone may integrate it for any financial instrument. Before mainnet,
decide once what the permanent contracts must support, testing the design against two reference
use cases (pools settlement and CKB-collateral lending).

## Demand Evidence
- **Real, named:** the team's own up/down pools product (not live). It cannot launch on mainnet
  without a price source that settles each round at an exact boundary. The settlement rule is
  defined once, under Recommended Approach item 6.
- **Reasoned, not yet named:** CKB-collateral lending. Founder: "without ckb price feed using CKB
  which is the most liquid asset for things like lending would be almost impossible." No lending
  team has asked yet.
- **Hypothetical:** the oracle "would spark varying finance primitives on CKB". Treated as upside,
  not a design driver.
- No outside users yet; testnet has one publisher (quorum 1).

## Status Quo
Nothing workable today. The 0.x Pyth relay was rejected because:
- cost: about **$800+/month** to run;
- possible legal/terms restrictions on using Pyth data this way (unverified; see Open Questions);
- no CKB/USD-type pairs, which lending needs.

## Target User & Narrowest Wedge
- Users: anyone building on CKB (open source, permissionless integration). Reference use cases:
- First user: the team's pools product, which needs a BTC/USD settlement price per round boundary.
- Second user: a CKB-collateral lending market, which needs CKB/USD (today CKB/USDT × USDT/USD).
- Wedge: pools settle every round on mainnet from Lean Oracle, with fewer VOID rounds and lower
  cost than the 0.x path.

## Constraints
- Contracts (`price_feed_type`, `publisher_set_type`) are immutable `data2` code; a fix means a new
  code hash and a migration. Nothing is public, so formats may change freely now.
- Publishers: 1 today; recruiting 4–7 independent operators is still open.
- Verification cost today: ~8M cycles per signature per feed (24M at 3-of-4, 56M at 7-of-9).

## Premises
1. v1 is **general-purpose open infrastructure**: anyone can integrate it for any instrument.
   The design is tested against two reference use cases, **(a) pools settlement** (exact-time
   settlement) and **(b) CKB-collateral lending** (several prices at once, CKB/USD). Features
   that help these patterns (cheap multi-feed reads, windowed feeds, rotation-safe history) help
   any integrator. *(Revised twice: the founder rejected pools-only, then two-users-only.)*
2. **Hypothesis:** v2 beats the Pyth path for CKB on total cost, legal exposure and native CKB
   pairs. The founder holds this firmly (cost, legal and CKB-collateral reasons; Codex challenged
   it). The CKB-pairs part is structural; cost is tested by the benchmark; the legal part is an
   open question to check against Pyth's terms.
3. Contract decisions must be settled before mainnet.
4. Pools settle on a windowed price (e.g. 60 s ending at the boundary), not a 1 s instant, because
   single-instant settlement can be pushed in the final seconds.

## Cross-Model Perspective
Codex (cold read):
- Steelman: settlement infrastructure that makes short-duration financial products viable on CKB,
  with pools as the proving ground.
- Most revealing answer: "cost and it does not have ckb/usd kind pairs", because pools need
  BTC/USD, so CKB pairs don't justify v2 for pools.
- Challenged premise 2; proposed proving the edge with numbers.
- Prototype: a BTC/USD round-settlement slice with a 60 s trailing window, replaying 1,000 rounds
  (missing ticks, publisher downtime, final-second spike, rotation between signing and
  settlement), recording settled vs VOID rounds, latency, cycles, fees and storage.

## Approaches Considered
- **A: Pools-first patch.** Rejected: leaves lending's double signature cost and per-feed
  verification frozen forever.
- **C: Basket cells.** Rejected: large SDK/docs change and does not fix rotation by itself.

## Recommended Approach
**B: v1 contract freeze, tested against the pools and lending reference cases.** One design pass over everything that becomes
permanent, then prove it with the benchmark and redeploy testnet as v3.

**Oracle-side parameters, not app parameters.** Window length, boundary schedule and the minimum
rotation interval are Lean Oracle protocol settings with defaults chosen for the oracle itself
(proposed: 60 s windows, a windowed value at every minute boundary, a rotation interval of a few
hours). Integrators build their own settlement deadlines and VOID rules on top of these
guarantees. No oracle decision waits on any single application.

Items to lock (each gets its detailed design in /plan-eng-review):
1. **Rotation-safe history.** The committee cell keeps the previous set and the first tick of
   the current set, so an update signed by the set that was current at its tick still verifies
   after one rotation. Because only one previous set is kept, the type script also enforces a
   **minimum interval between rotations**, longer than the pools settlement deadline. It is
   measured with CKB's `since` field: a rotation must spend the committee cell with a relative
   timestamp `since` ≥ the interval, so the chain itself proves the cell is at least that old.
   Together these guarantee no round is voided by rotation. The benchmark includes a
   two-rotations case, and a ckb-testtool case rejects a rotation with a missing or short `since`.
   **Emergency trade-off:** the interval also delays replacing a compromised key. The emergency
   lever is the pause (item 2), which is exempt from the interval: pause at once, then rotate once
   the interval has passed. Accepted consequence: a compromised key stays in the set, paused,
   until the interval ends.
2. **Pause.** A quorum-authorized pause/unpause that does not bump `set_index`, does not require
   PoP from every key, and is not subject to the rotation interval. Because it is the emergency
   lever (item 1), dropping the flag is no longer an option. /plan-eng-review decides the exact op
   and whether unpause needs a higher quorum.
3. **Committee cell lock.** A lock that cannot veto quorum-approved rotations, or a publisher
   multisig. /plan-eng-review decides, using this criterion: pick always-success only if the
   type-script guarantees below are cheap and fully tested; otherwise use a publisher multisig.
   If an always-success lock is chosen, the type script must first guarantee every
   path: reject destruction (already true), require exactly one continuing output with the same
   type, and forbid lowering capacity. All of these become ckb-testtool rejection cases.
4. **Multi-feed verification.** One quorum signature check per transaction covers several feed
   cells, so reading N prices costs about the same as reading one (signatures are ~8M cycles
   each; Merkle proofs are cheap). What is signed does not change: the header binds the committee, `set_index`, tick and
   Merkle root; each feed cell must match a leaf with a valid proof under that one header. The
   script verifies the signature once and rejects any feed cell whose leaf is not under the same
   header, so cells from different updates cannot be mixed. Replaying a subset is harmless:
   every cell still moves forward only. Mix and replay cases become rejection tests.
5. **Committee layout for lending.** CKB/USD needs CKB/USDT and USDT/USD from the same
   committee (one signature check). E.g. USDT/USD is also served by the `ckb` committee.
6. **Windowed feeds and the settlement rule.** A TWAP60 feed is a separate, optional feed: the
   time-weighted average of the last 60 one-second prices, much harder to push than a
   single second. Any integrator may use it. Pools settle on a windowed feed such as
   `Crypto.BTC/USD.TWAP60`: the update of that feed whose `publish_time_ms == boundary × 1000`.
   Its price is computed off-chain by each publisher as the time-weighted average of the feed's
   **finalized** 1 s prices over the 60 s ending at the tick, then signed as a normal leaf
   (median across publishers as today). Missing ticks inside the window are skipped. If fewer
   than 45 of 60 ticks are finalized the window is invalid, no TWAP leaf is signed for that
   boundary, and the pool takes its VOID path. **Cadence:** a TWAP60 leaf is added only to the
   updates at boundary ticks (the committee config names the boundary schedule, e.g. every
   minute), not every tick, so signing load and blob size barely change. **VOID deadline:** if
   no update with the boundary TWAP leaf exists by the pool's settlement deadline (from the
   Assignment), the round is VOID. Window length, threshold and schedule are oracle defaults
   decided in /plan-eng-review; the deadline belongs to each integrator.
7. **Format names.** Replace the `TPOU`/`TPOB` magics with Lean Oracle names.

**Lending: what the freeze provides vs what stays with the consumer.**
- Frozen formats provide: `publish_time_ms`, `source_time_ms`, `conf`, `expo` per feed, and
  same-committee CKB/USDT and USDT/USD in one signed update (so they share one tick).
- Consumer-side (documented in `lean_oracle_common::consumer`, not frozen): max-age rule against
  a header dep, same-tick pairing (require equal `publish_time_ms`), rescaling to a common
  exponent with explicit rounding, combining confidences, and USDT depeg handling (e.g. refuse
  when USDT/USD leaves a band).

**Mainnet gate.** Mainnet does not launch with quorum 1. It requires n ≥ 4 independent publishers
(quorum 3), or an explicit written acceptance of the quorum-1 risk.

## Open Questions
- Are 60 s / 45-tick minimum / minute boundaries the right oracle defaults? (/plan-eng-review + benchmark decide.)
- Do Pyth's data terms actually restrict this use? Check before citing it as a reason.
- Pause: add an op, or drop the flag?
- Committee cell lock: always-success or publisher multisig?
- Where do publishers 2–7 come from? (Mainnet gate above.)
- Does multi-feed verification share one witness across feed cells, or use a verification cell?
- Storage/retention policy for publisher and mirror (separate P0 fix in progress).

## Success Criteria
- **Benchmark setup:** input is recorded testnet finalized updates (the mirror's history) plus a
  devnet committee (`apps/deploy` e2e harness) for injected scenarios: publisher downtime (stop
  containers), missing ticks (drop finalized updates), a final-second spike (mock venue source),
  one rotation and two rotations between boundary and settlement (rotation CLI).
- 1,000 replayed rounds: zero VOID rounds caused by rotation; the two-rotation case is rejected
  by the minimum interval; VOID only when fewer than the minimum window ticks exist.
- A +5% spike on one venue for the final 2 s of a window moves the TWAP60 settlement price by
  less than 10 bps.
- A CKB/USD price for lending costs **one** quorum signature check.
- Total monthly cost compared like for like: Lean Oracle (publishers + mirror infrastructure +
  on-chain settlement fees at the pools' round cadence) vs the 0.x path (~$800+/month plus its
  on-chain fees).
- `publisher_set_type` has a ckb-testtool suite covering every rejection path.

## Distribution Plan
Existing pipeline: contracts via reproducible build + `apps/deploy`; SDK to npm by tag
(`sdk-v*`, OIDC); publisher/mirror/watchdog images to GHCR. The freeze ships as testnet v3 and
SDK 2.0.0 (1.0.0 is treated as throwaway; no compatibility kept).

## Dependencies
- P0 storage retention on the testnet droplet (separate task).
- The pools repo is out of scope for these sessions; the benchmark uses a minimal testnet
  settlement consumer in this repo (like `examples/price_trigger_lock`).

| Choice | Current | A | B | C |
|---|---|---|---|---|

Section 1 note (required proof of D6, no new choice): in `price_feed_type` a burn (1 -> 0) returns success without verifying anything, so a follower must never treat a burned feed input as its leader. ```
